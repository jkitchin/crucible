#+TITLE: Crucible Architecture
#+DATE: [2026-04-03 Fri]

* System Overview

Crucible consists of four layers:

1. *File system*: org-mode wiki articles and primary source files
2. *Database*: SQLite graph database tracking relationships
3. *Embeddings*: vector representations for semantic search
4. *CLI*: Python click commands for ingestion, search, and maintenance

The LLM (Claude Code via the crucible skill) sits above all four layers,
reading and writing files, querying the database via CLI commands, and
maintaining the knowledge base.

* Database Schema

The wiki graph database (=.crucible/crucible.db=) models three entity
types and their relationships. It holds nothing that is not in the
committed files: it is rebuilt from the wiki articles and
=.crucible/references.bib=, and a rebuild gives the same database.

** Entity Tables

*** sources

Primary source documents (papers, notebooks, data files).

Source rows are derived from =references.bib= and the files on disk. An
entry with a =file= field owns the row for that file, keyed by its cite
key, and the row's title, authors and date come from the entry. Files in
=sources/notebooks/= and =sources/data/= that no entry claims get a row
from a disk scan, keyed =<stem>= or, when that key is already a bib key or
another source's key, =<stem>-<ext>= (then =-2=, =-3=, ...). An entry
without a =file= field gets no row.

The bibliography is read with one brace-balanced parser
(=src/crucible/bibtex.py=). Entries may be delimited with braces or
parentheses, compact one-line entries such as doi.org returns are read
correctly, and =@comment=, =@string= and =@preamble= blocks are ignored.
An entry that is never closed is skipped (and reported by =crucible
lint=) without swallowing the entries after it.

| Column | Type | Description |
|-----------+---------+----------------------------------------|
| id | INTEGER | Primary key |
| path | TEXT | Path relative to the project root (=.crucible/sources/...=) |
| title | TEXT | Source title |
| source_type | TEXT | pdf, web, notebook, data, other |
| shareable | INTEGER | 0 = external/gitignored, 1 = shareable |
| url | TEXT | Original URL (optional) |
| authors | TEXT | JSON array |
| date | TEXT | ISO date |
| ingested_at | TEXT | Timestamp |
| metadata | TEXT | JSON blob for extras |

*** articles

Distilled wiki articles (the org files in =wiki/=).

The timestamps come from the article's properties drawer, so a rebuild
reproduces them: =created_at= from =:CREATED:= and =updated_at= from
=:MODIFIED:=, which falls back to =:CREATED:=. An article with only
=:MODIFIED:= uses it for both. With neither, sync uses the time of the
sync, which a rebuild cannot reproduce (=crucible lint= reports it).

| Column | Type | Description |
|---------------+---------+-------------------------------|
| id | INTEGER | Primary key |
| path | TEXT | Path relative to the project root (=.crucible/wiki/...=) |
| title | TEXT | Article title |
| article_type | TEXT | concept, summary, comparison, method |
| status | TEXT | draft, reviewed, verified |
| created_at | TEXT | From =:CREATED:= |
| updated_at | TEXT | From =:MODIFIED:= |
| distill_model | TEXT | Which LLM produced it |
| abstract | TEXT | Brief summary |

*** concepts

Named topics that articles can be tagged with, extracted from =#+FILETAGS=.

| Column | Type | Description |
|---------+---------+------------------------------|
| id | INTEGER | Primary key |
| name | TEXT | Canonical name (unique) |
| aliases | TEXT | JSON array of alternate names |

** Relationship Tables

*** article_sources

Many-to-many: which sources an article was distilled from.

*** article_concepts

Many-to-many: which concepts an article covers.

*** article_links

Directed graph: explicit cross-references between articles, extracted
from =[[file:...]]= links in the org files.

*** article_derivations

Tracks knowledge evolution: article Y was synthesized from articles
A, B, C at a given time. Extracted from the =:DERIVED_FROM:= property.

| Column | Type | Description |
|------------+---------+------------------------------|
| derived_id | INTEGER | The synthesized article |
| source_id | INTEGER | One of its input articles |
| derived_at | TEXT | When the derivation happened |

** Full-Text Search

The =article_fts= virtual table uses SQLite FTS5 with porter stemming
tokenization. It stores article path, title, and full text content;
queries match only title and content (a column filter), since the words
of a path such as =.crucible/wiki/concepts/x.org= are in every article.
Populated by =crucible sync=.

** Embeddings

The =embeddings= table stores vector representations generated by ollama.

| Column | Type | Description |
|------------+---------+--------------------------------|
| article_id | INTEGER | References articles(id) |
| model | TEXT | Embedding model name |
| dimensions | INTEGER | Vector dimensionality (e.g. 768) |
| vector | BLOB | Packed float32 array |
| updated_at | TEXT | Timestamp |

An article has at most one embedding. The vector column is an untyped
BLOB, so models of any dimension can be stored; older databases whose
column was =F32_BLOB(768)= (with a libSQL vector index) are migrated to
this layout, keeping their rows, the next time =crucible embed= or
=crucible search= opens the table.

What is embedded is the article text with its org header (=#+KEYWORD:=
lines, the title kept as the first line) and drawers such as
=:PROPERTIES:= removed, truncated to its first 8000 characters. Long
articles are therefore represented by their opening sections only.

* Search Architecture

** FTS5 Keyword Search

Standard SQLite full-text search with porter stemming. The query is
matched against article title and content. Each word is quoted, so FTS5
syntax in a query is literal text, except that a trailing =*= makes a
word a prefix query. Results are ranked
by BM25 (SQLite's default FTS5 ranking).

** Semantic Vector Search

1. The search model is the one given with =--model=, or else the model
   that most stored embeddings were made with, so a query is embedded
   with the same model as the articles unless asked otherwise.
2. The query is embedded by ollama (=--url= or =$CRUCIBLE_OLLAMA_URL=,
   default =http://localhost:11434/api/embed=).
3. libSQL's =vector_distance_cos= ranks the embeddings of that model and
   dimension; embeddings from other models are ignored. If the model's
   stored vectors have a different dimension from the query's, search
   stops with an error asking for =crucible embed --force=.

This is a brute-force scan in SQL (no approximate-nearest-neighbour
index), appropriate for knowledge bases up to a few thousand articles.

If the embedding service cannot be reached or lacks the model, the
default =auto= mode warns on stderr and falls back to FTS; the explicit
=semantic= and =hybrid= modes exit with an error.

** Hybrid Search with Reciprocal Rank Fusion

Both FTS and semantic search produce ranked lists. These are merged
using Reciprocal Rank Fusion (RRF):

For each article appearing in either list:
=score = fts_weight / (k + fts_rank) + semantic_weight / (k + semantic_rank)=

Where =k = 60= (the standard RRF constant that dampens rank differences).
Articles found by both methods get contributions from both, so they
naturally rank higher.

The weights are configurable via =--fts-weight= and =--semantic-weight=.

** Cross-Crucible Search

FTS5 virtual tables cannot be queried across SQLite ATTACH boundaries
with the MATCH operator. Instead, =search --all= opens a separate SQLite
connection to each registered crucible's database and runs the query
there. Results from all connections are merged and re-ranked.

* Org-Mode Parser

The lightweight parser in =src/crucible/orgparse.py= extracts metadata
from org files without requiring Emacs. It handles:

- =#+TITLE:= keyword
- =#+FILETAGS:= keyword (colon-delimited tags)
- =:PROPERTIES:= drawers (key-value pairs within drawer boundaries)
- =[[file:...]]= links (with optional =::= anchors)
- =cite:=, =citep:=, =citet:= org-ref citations

It is not a full org-mode parser. Complex structures (nested drawers,
inline properties, dynamic blocks) are not supported but are not needed
for crucible's metadata extraction.

* Sync Process

=crucible sync= first reconciles the sources table with =references.bib=
and the disk scan (see the sources table above), then operates in two
passes to avoid foreign key violations:

1. *Pass 1*: scan all org files, register/update articles in the database,
   create concepts from filetags, and link articles to concepts.
2. *Pass 2*: process inter-article links (=[[file:...]]=), source links
   (=:SOURCE_KEYS:=), and derivation chains (=:DERIVED_FROM:=).

The two-pass approach ensures all articles exist before cross-referencing.

* Global Registry

Crucibles find each other through the global registry,
=~/.crucible/registry.json=, rather than through anything stored in a
project's database. Each entry maps a name to the project's absolute
path, with an optional description and the time it was registered.
=crucible init=, =sync= and =update= register the current project, and
=crucible registry= lists, adds, removes and cleans entries (=clean= drops
those with no database on disk).

An entry also records its =origin=, where the crucible comes from. On
every registration it is read from the git =origin= remote of the
checkout the project is in (=git remote get-url origin=); without one, an
origin given by hand (=registry add --origin=) is kept. URLs are scrubbed
of credentials before they are stored. =crucible clone= sets the origin to
the URL it cloned, and adds =cloned_at=; =crucible pull= sets =pulled_at=.

Crucibles from elsewhere travel as git repositories: the wiki,
=references.bib=, notebooks and data are committed, while the database
and =sources/external/= are not. =clone= runs =git clone=, rebuilds the
database from the committed files (the same rebuild =get_root()= does
for a missing database) and registers the result. =pull= fetches and
fast-forwards the clone, then syncs it. A clone is treated as a read-only
peer: pull refuses one with tracked changes or commits of its own, except
=MANIFEST.md= and =index.org=, which sync regenerates with the date and
pull resets before updating. Folding a clone's content into another
crucible is left to =merge=.

When =--all= is used on =search= or =concepts=, crucible opens a separate
connection to each other registered crucible's =.crucible/crucible.db=
and runs the query against it. Results are tagged with the crucible's
registry name and merged with local results. A peer left out (no
database on disk, or one that fails to open or query) is named in a
warning on stderr; =get_peers(skipped=...)=, =CrucibleDB.peer_warnings=
and =EmbeddingIndex.warnings= collect the reasons.

Peer results are untrusted. A peer's wiki was written by someone else, and
search output is often read by an agent, so a peer article is data to be
read, never instructions. =_mark_peer_rows= tags every row of an =--all=
listing with =_untrusted= (and a peer's with =_origin= and =_abs_path=),
and the text output ends with a notice whenever a peer contributed. The
skill tells agents not to act on instructions found in peer content.

No data is written to other crucibles' databases. The connection is
read-only by convention (SQLite's default mode allows writes, but
crucible never issues write queries against those connections).
